- **Prove the greedy choice before coding it.** State out loud why picking the locally best option can never make the final answer worse — an exchange argument ("if the optimal solution didn't make this choice, swap it in and show it's no worse") is the standard proof technique in interviews.
- **Sort by the right key.** Most greedy problems hinge entirely on choosing the correct sort key (end time vs. start time, ratio vs. absolute value). Getting the key wrong silently breaks correctness while the code still runs.
- **Track running state, not history.** Greedy needs O(1) extra state (current max reach, running sum, open range) rather than remembering every past decision — that's what keeps it O(n) after the sort.
- **Test on a small adversarial case.** Before trusting a greedy idea, try 3-4 handmade elements where the "obvious" local choice could plausibly fail. If it still works, you likely have the right invariant.
- **Watch for off-by-one at the boundary.** Reachability problems (Jump Game) often fail by comparing `i <= maxReach` vs `i < maxReach`, or by forgetting to update `maxReach` before checking if the loop should terminate early.
- **Reset behavior matters.** Gas-station-style problems reset the running total (and the candidate start index) the moment it goes negative — forgetting to reset the start index, not just the sum, is a classic bug.
- **Pitfall — greedy without proof.** The most common interview mistake is assuming greedy works because it "feels right." If you can't articulate why the local choice is safe, sketch a DP alternative first, then look for the greedy shortcut.
- **Pitfall — multiple greedy passes.** Some problems (Candy) need two greedy sweeps — left-to-right then right-to-left — because a single direction can't see both neighbors at once. Recognize when one pass isn't enough.
