- **Pick the invariant first.** Decide exactly what "valid window" means (sum ≤ target, ≤ k distinct chars, at most k replacements) before writing the loop — the whole shrink condition falls out of that one sentence.
- **Shrink with a `while`, not an `if`.** A single bad element can require popping several from the left before the window is valid again; `if` only fixes one step and silently produces wrong answers.
- **Track the answer at the right moment.** For "longest valid window," update the answer *after* the shrink loop, once the window is guaranteed valid. For "count of valid windows ending at right," every value of `left` from 0 to the current `left` contributes — add `left + 1` (or `right - left + 1`) to the count, don't just check the final window.
- **Frequency map + a single "valid" counter beats rescanning.** Keep a count map and one integer like `distinct` or `matched`; update that counter incrementally as characters enter/leave instead of comparing whole maps in the loop — comparing maps every step silently turns O(n) into O(n·26).
- **Exactly-K trick:** "exactly K distinct/odd/etc." is usually `atMost(K) - atMost(K - 1)` — two clean at-most-K windows instead of one fiddly exactly-K window.
- **Fixed-size window:** when width `k` is given, add the incoming element and remove the outgoing one every step; don't recompute the sum/count from scratch each time.
- **Pitfall — off-by-one on window length:** window size is `right - left + 1`, not `right - left`. Double-check this in every fixed-size or size-tracking window.
- **Pitfall — forgetting to shrink back on an invalid entry:** if the entering element itself violates the constraint (e.g. duplicate char), make sure the shrink loop can move `left` past *and including* its previous occurrence, not just by one.
