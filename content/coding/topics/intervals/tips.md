- **Sort by the right key.** Merge/insert problems sort by **start**; greedy "max non-overlapping" or "min arrows" problems sort by **end** — picking the wrong key silently breaks the greedy proof.
- **Overlap check, memorized:** two intervals (sorted by start) overlap iff `b.start <= a.end`. Get this comparison operator (`<=` vs `<`) right for "touching" edge cases — do adjacent intervals like `[1,2]` and `[2,3]` count as overlapping for this problem?
- **Merge in place with `max`, not just extension:** when merging, the new end is `max(current.end, next.end)` — a fully-nested interval like `[2,3]` inside `[1,10]` must not shrink the merged range.
- **Sweep-line for counting concurrency:** for "how many meetings overlap at once," split each interval into a `+1` start event and a `-1` end event, sort all events, and scan while tracking a running counter — this gives min rooms / max concurrency without ever pairing intervals up explicitly.
- **Greedy-by-end-time proof:** for "maximum non-overlapping intervals," always keep the interval that ends earliest among candidates — it leaves the most room for future picks. This is the same idea behind "minimum arrows to burst balloons."
- **Two pointers for intersecting two lists:** when both lists are already sorted, advance whichever interval ends first — no need to re-sort or use extra space.
- **Pitfall — mutating while iterating:** inserting into a sorted interval list needs three phases (copy intervals fully before the new one, merge all overlapping ones, copy the rest) — trying to splice in place mid-loop is a common source of off-by-one bugs.
- **Pitfall — forgetting to sort:** if the input says "intervals" without saying "sorted," assume it is not sorted; skipping the sort is the single most common wrong-answer cause in this pattern.
