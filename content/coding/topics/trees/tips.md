- **Always handle the null node first.** Recursive tree functions almost always start with `if node is None: return <base case>` — get the base case right (0, `True`, `float('-inf')`, etc.) before worrying about the recursive step.
- **Postorder for "combine children" problems.** Height, diameter, balanced-check, and max path sum all need each node to know its children's answers before computing its own — return the needed value from the recursive call rather than using a global/mutable accumulator when possible.
- **BST search prunes, plain tree search doesn't.** In a BST, compare the target to `node.value` and go left or right — O(log n) on a balanced tree. In a plain binary tree (e.g., LCA of a binary tree, not a BST), you must search both subtrees since there's no ordering to exploit.
- **Inorder = sorted order, only for BSTs.** "Kth smallest," "validate BST," and "convert BST to sorted list" all reduce to an inorder traversal; this trick does *not* apply to non-BST trees.
- **Validate BST needs a range, not just parent comparison.** Comparing each node only to its immediate parent misses violations from a grandparent — pass down a `(low, high)` bound and shrink it as you descend.
- **BFS needs a queue and a level-size snapshot.** For level-order problems, capture `len(queue)` at the start of each level before popping, otherwise nodes from the next level bleed into the current one.
- **Recursion depth is O(height), not O(n).** A skewed tree (essentially a linked list) can blow the recursion stack at n ~ 10⁴–10⁵ — worth a sentence about iterative traversal with an explicit stack if asked about worst case.
- **Pitfall — mutating while traversing.** Deleting a node or flattening a tree in place can lose references to subtrees if you overwrite `left`/`right` before you've saved what they pointed to.
- **Reconstruction needs a fast index lookup.** Building a tree from preorder+inorder (or similar) is O(n²) with naive `list.index()` calls — precompute a value→index map for inorder to get O(n).
